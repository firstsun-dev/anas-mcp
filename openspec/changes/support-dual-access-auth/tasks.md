2026-10-14 (PR #10 third review follow-up, branch `feat/dual-access-auth`):
- OpenAPI OAuth scheme corrected again: the `openIdConnect`/`openIdConnectUrl` fix immediately below was itself the wrong OpenAPI vocabulary. `openIdConnect` names a full OpenID Connect Discovery document; Cloudflare Access's Managed OAuth for MCP publishes plain OAuth 2.0 Authorization Server Metadata (RFC 8414) plus RFC 9728 protected-resource metadata, not OIDC. Checked the authoritative OAS 3.2 spec directly (`https://spec.openapis.org/oas/v3.2.0.html` §4.27.1 and the published JSON Schema at `https://spec.openapis.org/oas/3.2/schema/2026-08-30`, fetched and read): OpenAPI 3.2 added `oauth2MetadataUrl` to the `oauth2` Security Scheme Object precisely for an authorization server with RFC 8414-discoverable (rather than fixed) endpoints. The schema requires the `flows` key to be present for `type: oauth2`, but the referenced `oauth-flows` sub-schema has no `required`/`minProperties` constraint, so `flows: {}` is schema-valid without fabricating an `authorizationUrl`/`tokenUrl`.
- `CloudflareAccessOAuth` is now `type: oauth2`, `oauth2MetadataUrl: https://mcp.firstsun.org/.well-known/oauth-authorization-server`, `flows: {}`. Verified two independent ways: (1) `redocly lint` passes with 0 errors, and its strictness was empirically confirmed by temporarily injecting a bogus field into the same scheme object (rejected) and temporarily removing `flows` (rejected, "must be present"), so its clean pass on the real shape is meaningful, not a leniency artifact; (2) downloaded the real OAS 3.2 JSON Schema + its dialect/meta vocabulary documents from `spec.openapis.org` and validated `openapi.yaml` against them directly with `ajv`/`ajv-formats` (`Ajv2020`) — zero errors reference `CloudflareAccessOAuth`, `oauth2MetadataUrl`, or `flows`; the only errors produced are pre-existing `$dynamicRef`/`unevaluatedProperties` artifacts affecting unrelated, untouched nested Schema Objects throughout the whole document (even `HealthResponse`), which is a known category of AJV limitation with OAS 3.2's dynamic-scoping dialect and not something `redocly` (which correctly validates those same schemas) reproduces. This ad hoc AJV cross-check required live network fetches of the spec documents, so it is not wired into `npm run check` (would not be deterministic/reproducible in CI); it is recorded here as supplementary manual evidence, not an automated gate.
- `tests/openapi-contract.test.ts` rewritten to assert the current, correct shape: `type: oauth2`, `oauth2MetadataUrl` equal to the real discovery URL, no `openIdConnectUrl`, `flows` present and empty, and that no flow object ever gains a fabricated `authorizationUrl`/`tokenUrl`, plus the existing Mode A (OR) / Mode B (AND) `/mcp` security-requirement check.

2026-10-14 (PR #10 second review follow-up, branch `feat/dual-access-auth`):
- OpenAPI OAuth endpoint honesty: the 2026-10-13 fix below still set `CloudflareAccessOAuth`'s `authorizationUrl` AND `tokenUrl` to the same RFC 8414 discovery document URL. That document tells a client where the real endpoints are; it is not itself an authorize or token endpoint, so a real OAuth/Swagger client driving that flow against those URLs would break. Fixed by switching the security scheme from `oauth2` (which requires hard-coded `authorizationUrl`/`tokenUrl`) to `openIdConnect` (`openIdConnectUrl` pointing at the discovery document) — confirmed via Cloudflare's "Managed OAuth" docs that Access genuinely does not publish fixed authorize/token endpoints for this flow, so no fixed-URL `oauth2` representation can be both complete and honest. `tests/openapi-contract.test.ts` (new, parses `openapi.yaml` with the `yaml` package, now a pinned `devDependency`) asserts the scheme is `openIdConnect`, is not `oauth2`, has no `flows` object, and that the discovery URL is never reused as a fabricated `cdn-cgi/access/oauth/...` path. Also corrected the `/mcp` `503` response description to cover JWKS-unavailable (not only missing config).
- JWKSInvalid misclassification: the 2026-10-13 fix below (see its bullet on JWT/JWKS error semantics) incorrectly listed `JWKSInvalid` (a structurally malformed/unusable *remote JWKS document*, thrown by `createLocalJWKSet`/`importWithAlgCache` after a successful HTTP fetch) alongside `JWKSNoMatchingKey` as a `401` case. That was a bug: `JWKSInvalid` means Cloudflare's own key document is broken, which is a provider-availability failure, not evidence about the caller's token. Fixed in `src/auth/cloudflare-access.ts` by adding `JWKSInvalid` to the `503`/`unavailable` branch, next to `JWKSTimeout` and the generic fetch-failure `JOSEError`. `JWKSNoMatchingKey` (wrong/unknown `kid` on an otherwise well-formed JWKS) correctly remains `401`. `tests/mcp-auth.test.ts` updates the test that previously asserted the buggy 401 behavior for `JWKSInvalid` to assert `unavailable`/503 instead, and adds a dedicated case for an HTTP-failure-shaped generic `JOSEError`. Traced every error-construction site in the installed `jose` package (`node_modules/jose/dist/webapi/{jwks/remote.js,jwks/local.js,lib/jws_verify.js,lib/validate.js}`) to confirm client-side JWT/JWS parsing errors (malformed token, bad base64url, bad header JSON, bad signature) are always wrapped in `JWSInvalid`/`JWTInvalid`-family errors, never raw exceptions, so the `!(error instanceof JOSEError)` branch cannot accidentally reclassify an arbitrary client parse error as `503`.
